# Кафедральная платформа C++17

Django 5.2 LTS, SQLite, серверные HTML-шаблоны, отдельный Docker-worker. Закреплён исправленный [Django 5.2.18](https://www.djangoproject.com/weblog/2026/oct/06/security-releases/); версии остальных пакетов сверены с PyPI. До 30 студентов, один сервер, один worker. Студент сдаёт программы и теорию; преподаватель готовит работы и оценивает ответы в Django Admin.

**Статус проверки:** [docs/verification.md](docs/verification.md). Проверки выполняются на отдельной файловой SQLite, в настоящем Docker и Chromium. Репетиция 30 студентов с перезапуском worker после улучшений: максимум ожидания 57.9 с, p95 HTTP 1.37 с на демонстрационной задаче с тремя тестами. Проверена сдача через браузер и восстановление копии; реальные задания нужно измерять отдельно. Для собственного набора задач используйте `scripts/rehearse_exam.py --problem-json /закрытый/путь/problem.json`.

## Локальный запуск

Требуются Python 3.12 и доступ к PyPI. Docker нужен только для проверки C++, веб-приложение запускается без него.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
export DEBUG=1
.venv/bin/python manage.py migrate
.venv/bin/python manage.py configure_sqlite
.venv/bin/python manage.py createsuperuser
.venv/bin/python manage.py seed_demo --teacher admin
.venv/bin/python manage.py runserver
```

Вместо `admin` укажите созданный логин. Вход: <http://127.0.0.1:8000/>; админка: <http://127.0.0.1:8000/admin/>. Создайте студента в админке и добавьте в «Демонстрационную группу». Общего демонстрационного пароля нет.

В другом терминале, с теми же `DEBUG=1`, `DATABASE_PATH` и виртуальным окружением:

```bash
docker build -t contest-judge:local judge
.venv/bin/python manage.py judge_worker
```

Без Docker отправка сохраняется, проверка не выполняется. Worker не запускает студенческий код или компилятор на хосте. Если проверка уже завершилась ошибкой инфраструктуры, преподаватель повторно ставит её в очередь через действие в списке отправок.

## Сервер и HTTPS

Требуются Linux, Docker Engine с Compose v2, работающие memory/PID limits, 2 CPU, желательно от 4 ГБ RAM, локальный SSD. Это стартовая конфигурация; фактическую скорость очереди нужно измерить на задачах кафедры. SQLite хранится на локальном диске, не на NFS. Reverse proxy Caddy автоматически получает и продлевает TLS-сертификаты.

```bash
cp .env.example .env
python3 -c 'import secrets; print(secrets.token_urlsafe(64))'
stat -c '%g' /var/run/docker.sock
```

Запишите сгенерированный `SECRET_KEY`, имя сервера `DOMAIN` и группу сокета `DOCKER_GID` в `.env`. DNS должен указывать на сервер, порты 80/443 — быть открыты. Значения сгенерированного secret не публикуйте. Без production secret приложение не запускается.

```bash
docker compose build web worker judge-image
docker compose up -d
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py seed_demo --teacher admin
docker compose logs -f worker
```

Compose запускает миграции, включает WAL, собирает статику, затем запускает веб, worker и proxy. Веб доступен только внутри Compose и не получает Docker socket. Только worker получает сокет; доступ к нему даёт управление Docker хоста. Для этой роли используйте отдельный учебный сервер. Контейнеры студентов не получают сокет или секреты приложения.

Не масштабируйте worker: общая файловая блокировка разрешает один процесс. При нескольких установках на одном daemon задавайте разные `JUDGE_PREFIX`, отдельные базы и блокировки. Проверки используют именованные Docker volumes: пути файловой системы worker не должны совпадать с путями хоста.

Обновление:

```bash
docker compose stop web worker
docker compose build web worker judge-image
docker compose run --rm init
docker compose up -d web worker proxy
```

Перед обновлением сохраните резервную копию. Для воспроизводимого развёртывания сохраняйте собранные образы вместе с версией исходников; Python-зависимости закреплены точно, базовые Docker-теги получают обновления. В рабочей инфраструктуре можно закрепить проверенные образы по digest.

## Подготовка работы

1. Суперпользователь создаёт преподавателя (`is_staff=True`). Преподаватели имеют доступ ко всем учебным данным. Они могут создавать студентов и группы, но назначать административные права может только суперпользователь.
2. В «Problems» создайте задачу: условие обычным текстом или Markdown, время 0.1–10 секунд, память 32–512 МБ. При необходимости заполните входные/выходные данные, ограничения и стартовый код C++17. Кнопка «Предпросмотр условия» открывает несохранённый текст отдельно. Добавьте открытые примеры и скрытые тесты (не более 100 суммарно, хотя бы один скрытый).
3. В «Assessments» создайте лабораторную или зачёт, назначьте группы, даты, продолжительность зачёта, проходной балл и правила раскрытия результатов. Добавьте задачи с баллами и обязательностью. Сохраните.
4. Добавьте теоретические вопросы; при необходимости свяжите с уже сохранённой задачей. Сохраните.
5. В форме работы нажмите «Сохранить и опубликовать». В списке работ также доступно действие «Опубликовать новую неизменяемую версию». Простое сохранение формы оставляет работу черновиком или сохраняет изменения без новой публикации. Если публикации мешает отсутствие тестов, форма покажет причину и сохранит введённые данные.
6. Убедитесь под студенческим аккаунтом, что работа видна, примеры корректны, а зачёт начинается только после страницы правил.

Изменения исходной задачи, тестов, вопросов, групп или правил не меняют опубликованное содержание. Повторная публикация создаёт новую версию для ещё не начавших студентов. Существующая попытка всегда использует свою версию и не сбрасывается. Назначение фиксируется списком групп; актуальное членство студента проверяется при старте. Начавшаяся попытка остаётся доступной владельцу и после смены группы.

Одна попытка на студента и работу. Срок — минимум общего закрытия и начала плюс продолжительность. Сервер проверяет срок под блокировкой записи. Черновики не оцениваются; код нужно явно отправить. Лимит оцениваемых отправок считается отдельно по задаче, примеры его не расходуют. Одновременно у студента допускается максимум три задания в очереди/проверке по всем работам. Ошибка инфраструктуры не даёт баллов; преподаватель повторяет ту же отправку без расхода нового слота лимита.

Досрочное завершение атомарно сохраняет все поля и закрывает попытку. При истечении срока учитываются уже сохранённые ответы и принятые отправки. Принятые вовремя отправки проверяются даже после завершения. При проблемах с сетью интерфейс сохраняет локальную копию и предлагает восстановление; браузерные данные доступны только в том же браузере и могут быть удалены его настройками. После дедлайна локальный текст можно скопировать, загрузить его на сервер уже нельзя.

В админке попытки есть «Продлить время». Укажите новый будущий срок и причину: старый/новый срок и автор остаются в журнале. Продлить можно и после дедлайна, в том числе за пределы общего закрытия; досрочно завершённую попытку это не открывает. При отложенном раскрытии оценки всё равно открываются по исходному общему закрытию версии.

## Рабочая страница и редактор

Условие и теория находятся слева, код — справа, примеры, результаты и история — под редактором. Задачи переключаются без перезагрузки; для каждой сохраняются собственный код и состояние редактора. Границу панелей можно двигать мышью или стрелками с клавиатуры. На узком экране панели располагаются вертикально.

Редактор — [Monaco Editor](https://github.com/microsoft/monaco-editor) 0.52.2: подсветка C++, номера строк, отступы, парные скобки, сворачивание кода, поиск, отмена/повтор, подсказки ключевых слов и сниппеты. Сервер языка C++ не подключён: анализ типов и диагностика ошибок до компиляции не выполняются. `Ctrl+S` / `⌘S` сохраняет код и теорию; в редакторе `Ctrl+Enter` / `⌘Enter` запускает примеры, с `Shift` — отправляет код на оценку.

Все JS/CSS, шрифт значков и worker редактора раздаются из `static/editor/` на том же сервере. Внешний CDN не требуется. Сборка уже включена в проект, поэтому обычному запуску Django и Compose Node.js не нужен. Если редактор не загрузится, обычное текстовое поле продолжит работать с автосохранением.

Для изменения редактора нужны Node.js 20+ и npm:

```bash
npm ci
npm run build:editor
```

Исходник адаптера — `frontend/editor.js`, сборщик — `scripts/build_editor.mjs`, версии закреплены в `package-lock.json`. После изменения адаптера включайте в изменения и пересобранные файлы `static/editor/`; при production-развёртывании выполните `collectstatic` или обычную команду обновления Compose. Лицензия Monaco и ThirdPartyNotices поставляются рядом со сборкой.

Опрос очереди получает только краткие сведения об отправках. Полный результат загружается отдельно для выбранной отправки с той же проверкой владельца и срока раскрытия. Это не передаёт браузеру скрытые тесты и не загружает повторно весь вывод каждые четыре секунды.

Вкладка «Свой ввод» позволяет передать программе `stdin` (до 64 КиБ UTF-8; пустой ввод разрешён). Кнопка «Запустить» создаёт отдельную отправку в общей Docker-очереди. Показываются ввод, stdout и stderr; вердикт успешного выполнения — «Выполнено», без сравнения с эталоном. Запуск не даёт баллов, не расходует лимит оцениваемых отправок и не связывается с ответом на теорию. Общий лимит трёх активных отправок и дедлайн действуют. Ввод восстанавливается в этом браузере отдельно для каждой задачи; уже запущенный ввод хранится вместе с отправкой.

Результаты открытых примеров показывают ввод, ожидаемый и фактический вывод, включая пустые значения. Проверка заканчивается на первом неудачном примере. Координаты `main.cpp:строка:столбец` в диагностике компилятора кликабельны: открывается строка текущего кода либо отдельный просмотр отправленного исходника, если черновик изменился.

Markdown обрабатывает сервер через `markdown-it-py==3.0.0` с отключёнными HTML и изображениями и встроенной проверкой URL. Условия, дополнительные разделы и стартовый код сохраняются в опубликованной версии. Старые версии продолжают отображаться как обычный текст. Стартовый код подставляется только при отсутствии черновика; пустой сохранённый черновик не заменяется.

## Кабинет преподавателя

Ссылка «Кабинет преподавателя» открывает `/teacher/` для активных пользователей с `is_staff=True`. Подготовка и публикация работ остаются в административных формах; из кабинета есть прямые переходы.

- Ведомость работы: фильтры версии и группы, состояние попытки, баллы по задачам, непроверенные ответы, общий балл и предварительность. По умолчанию выбрана текущая версия. Для неё показаны также ещё не начавшие студенты. Уже начатая старая версия доступна через переключатель; второй попытки по работе нет. Фильтр группы использует текущее членство, существующие попытки без фильтра не пропадают после изменения групп.
- Страница попытки: теория, связанный код, форма баллов и комментария, продление срока с причиной и журналом. Если студент изменил ответ после открытия формы, сохранение оценки отклоняется, введённый комментарий остаётся на экране.
- `/teacher/judge/`: сигнал worker, текущая отправка, размер очереди, ожидание самого старого задания и последние 20 инфраструктурных ошибок. Повторная проверка доступна только для таких ошибок и использует существующую отправку.

Worker записывает сигнал каждые 5 секунд, в том числе во время Docker-проверки. После 30 секунд без сигнала работающий процесс считается неизвестным; автоматического повторения задания нет. Штатная остановка и ошибка показаны отдельно. Панель обновляется раз в 5 секунд; при потере связи явно помечает данные устаревшими. Веб-процесс не обращается к Docker.

## Проверка теории и итог

Откройте «Theory answers», прочитайте вопрос опубликованной версии, ответ и связанную отправку. Введите утверждённый балл от 0 до максимума и комментарий. Пустому ответу тоже нужно явно назначить балл, например 0. Оценка открытого в устаревшей форме ответа отклоняется, если студент успел его изменить. Изменение текста или связи с кодом сбрасывает оценку. Новые отправки кода не меняют существующую связь ответа.

За программу — весь максимум при прохождении всех тестов или 0. Используется лучшая оцениваемая отправка. Итог включает теорию. Для зачёта нужны проходной балл и все обязательные программы. Пока попытка открыта, есть незавершённые проверки, ошибки инфраструктуры или ответы без оценки, результат предварительный. Преподаватель видит баллы и ссылку на итог в списке попыток.

Отложенное раскрытие скрывает вердикты оцениваемых отправок, диагностику компилятора и оценки до общего закрытия. Примеры остаются открытыми. Скрытые входные/ожидаемые/фактические данные не отправляются студенту ни в HTML, ни в JSON, даже после закрытия.

## Изоляция проверки

Компиляция C++17 выполняется один раз в контейнере с 512 МБ памяти и стеновым лимитом 30 секунд. Каждый тест — новый контейнер, без сети, с UID 65534, read-only корнем и read-only volume бинарного файла, без capabilities и с `no-new-privileges`. Лимиты: 1 CPU, 32 процесса, 64 файловых дескриптора, отсутствие core dumps, 16 МиБ на файл, ограниченный tmpfs, отсутствие swap и общий лимит stdout/stderr 64 КиБ. Лимит теста — указанное время плюс 0.75 секунды на запуск/подключение Docker. Сравниваются последовательности байтовых токенов, разделённых ASCII whitespace; специальных checker нет.

При завершении и ошибках контейнеры и volume удаляются. Логирование Docker для тестов отключено, чтобы чрезмерный вывод не заполнил диск daemon. После аварийной остановки следующий worker под эксклюзивной блокировкой помечает `running` как `infra_error`, удаляет оставшиеся ресурсы своей установки и только затем принимает новые задания. При недоступной очистке worker останавливается. Преподаватель может повторить прерванные проверки.

Интерфейсы будущих поставщиков вопросов и предложенных оценок находятся в `lab/providers.py`; предложенные баллы отделены от утверждённых. ИИ, WASM, заимствования, варианты и пересдачи в эту версию не включены.

## Проверки

```bash
# Независимые от Django unit-тесты runner; только доверенные тестовые Python-процессы.
python3 -m unittest tests.test_judge_unit tests.test_restore tests.test_backup_offsite -v

# Миграции, шаблоны, права, дедлайны, версии, оценки, конкурентные HTTP-запросы.
DEBUG=1 .venv/bin/python manage.py check
DEBUG=1 .venv/bin/python manage.py makemigrations --check --dry-run
DEBUG=1 TEST_DATABASE_PATH=/tmp/contest-tests.sqlite3 .venv/bin/python manage.py test lab.tests -v 2

# Реальный Docker: корректный/неверный код, CE, RE, цикл, вывод, память,
# дочерние процессы, сеть, read-only FS, свежая FS между тестами и очистка.
docker build -t contest-judge:local judge
RUN_DOCKER_TESTS=1 .venv/bin/python -m unittest tests.test_docker_integration -v

# В production-конфигурации после развёртывания:
docker compose exec web python manage.py check --deploy

# Тринадцать браузерных сценариев с настоящим Chromium и локальными статическими файлами.
# API в этом наборе подменён; права доступа и бизнес-правила проверяют Django-тесты.
npm ci
BROWSER_PATH=/usr/bin/chromium npm run test:browser
```

`BROWSER_PATH` должен указывать на установленный Chrome/Chromium; при другом пути Python задайте `PYTHON=/путь/к/python`. Браузерный набор использует отдельные контексты и демонстрационный HTML без обращения к рабочей базе. Проверяет переключение задач, Monaco, сохранение/восстановление, результаты, завершение, продление, мобильную раскладку, собственный ввод, диагностику, преподавательскую форму и обновление очереди; при успехе сохраняет снимки в `test-results/`. API подменено: эти сценарии не подтверждают реальную запись оценки или выполнение C++.

Конкурентные тесты требуют отдельную **файловую** тестовую БД: тест по умолчанию с SQLite in-memory будет пропущен. Команда создаёт и удаляет `/tmp/contest-tests.sqlite3`; не указывайте рабочую базу. Django-тесты заменяют результаты проверки только для проверки учебной логики; изоляцию C++ подтверждает отдельный настоящий Docker-набор.

Проведите также ручную проверку в браузере: вход студента, восстановление локального текста после потери сети, уход со страницы с несохранённым ответом, перезагрузка таймера, запуск примеров, явная отправка, связь теории с кодом, досрочное завершение и продление преподавателем. Полный сценарий сдачи готов к эксплуатации только после прохождения Django- и Docker-наборов на сервере.

## Надёжность перед зачётом

Сохранения кода и теории защищены версиями от перезаписи из устаревшей вкладки. При конфликте доступны сравнение текстов и явный выбор. Повтор неподтверждённой отправки использует тот же идентификатор и не расходует дополнительную попытку; браузер сохраняет запрос для повторения после перезагрузки. Ожидание ответа ограничено 15 секундами. Для обновления требуется миграция `lab.0003` и перезагрузка открытых студенческих страниц.

Репетиция с настоящими HTTP-запросами, Docker и проверкой восстановления:

```bash
.venv/bin/python scripts/rehearse_exam.py --students 30 --restart-worker --report test-results/exam-load.json
BROWSER_PATH=/usr/bin/chromium .venv/bin/python scripts/rehearse_exam.py --students 1 --browser --report test-results/exam-browser.json
```

Рабочая база не используется. Скрипт создаёт временную установку, проверяет повторы отправок, выставление теории, окончательный итог и резервное восстановление, затем убирает тестовые ресурсы. Подробности, ограничения нагрузки и настройка ежедневной копии с SSH-выгрузкой: [docs/operations.md](docs/operations.md).


## Улучшения надёжности и преподавательские инструменты

Для обновления нужна миграция `lab.0004`. Перед обновлением сохраните резервную копию и выполните обычную процедуру обновления Compose. Миграция заносит текущие оценки в журнал как исходное состояние; предыдущую историю восстановить из последнего значения невозможно.

- Ввод и ожидаемый вывод каждого теста проверяются по размеру UTF-8: не больше 64 КиБ каждый. Runner ограничивает суммарный stdout/stderr 64 КиБ; диагностический вывод программы также расходует этот лимит.
- Изменение и снятие оценки, а также её сброс после изменения ответа сохраняются в журнале с автором, баллами, комментариями, текстом и версией ответа, связанной отправкой. Журнал доступен в кабинете преподавателя и в административном разделе Grade changes.
- В карточке задачи есть необязательное поле «Эталонное решение C++17» и кнопка «Сохранить и проверить эталон». Worker проверяет сохранённый эталон на сохранённых тестах с текущими лимитами. При заполненном эталоне публикация требует успешной последней проверки этих данных. После изменения тестов, лимитов, эталона или имени образа проверку нужно повторить. После пересборки образа с тем же тегом также запустите проверку заново. Эталон и его результаты доступны преподавателям; в опубликованный студенческий документ эталон не включается. Студенческие отправки получают приоритет перед проверками эталонов.
- В кабинете есть импорт до 200 новых студентов за раз из CSV UTF-8. Обязательны `username,password,group`; дополнительно `first_name,last_name,email`. Файл полностью проверяется до записи, пароли проверяются стандартными правилами Django, существующие логины не перезаписываются. Колонки административных прав не допускаются.
- Ведомость выгружается в CSV с выбранной версией и группой. Текстовые значения защищены от интерпретации формул таблиц. В историю отправок добавлены отдельная страница и фильтр задачи; на странице работы загружаются только последние 50 кратких записей. Переключатель задач показывает черновик, отправку или принятие с учётом правил раскрытия.
- Вход студента и администратора используют общий лимит: 8 попыток на логин и 300 на IP за 15 минут. Успешный вход сбрасывает счётчик логина. Пороги задаются в `.env`; блокировка возвращает HTTP 429 с `Retry-After`. Compose доверяет `X-Real-IP`, который Caddy перезаписывает адресом соединения; при самостоятельном запуске доверие заголовку выключено. Лимиты охватывают все процессы Gunicorn через SQLite.
- Панель очереди предупреждает об ожидании от 120 секунд; порог — `QUEUE_WARNING_SECONDS`. Команда `python manage.py check_exam` возвращает JSON и ненулевой код при отсутствии worker или задержке очереди. Проверку свежести подтверждённой внешней копии можно добавить через `--backup-directory`. Настройка внешнего контроля: [docs/operations.md](docs/operations.md).

Ошибки Docker записываются в журнал worker с этапом, ограниченной диагностикой и идентификатором ресурса. Завершение каждой проверки содержит тип задания, его номер и статус; исходники и скрытые тесты в эти записи не включаются.
