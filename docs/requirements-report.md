# Проверка требований и сценариев зачёта

13 ноября 2026 года. Проверены код, серверные API, настоящий Docker-runner и Chromium. Рабочая база не изменялась: все прогоны используют временные SQLite и отдельные Docker-ресурсы.

## Что изменено

| Требование | Реализация |
| --- | --- |
| Общий вход по логину и паролю | Существующая аутентификация Django для обеих ролей, разграничение доступа по предметам и владельцу попытки |
| Предметы | Название, группы, преподаватели, описание с критериями, FAQ; отдельные закрытые критерии приёма для преподавателей |
| Список практических работ | Переход из предмета к его работам; дедлайны работ и ближайший дедлайн предмета |
| Практическая работа / зачёт | Название, дата и время открытия, дедлайн начала попыток, группы, индивидуальный допуск студента, баллы заданий, проходной балл, необязательные пороги оценок |
| Состав и порядок | В одном списке тесты и задачи, порядок задаётся числом; линейная зависимость без графов, ветвлений и циклов |
| Условия до старта | Отдельный экран задания с временем, попытками, правилами возврата, порогом и обязательностью проверок |
| Дедлайн | Ограничивает начало новых попыток. Уже начатая попытка сохраняет полный учебный таймер после дедлайна |
| Тесты с вариантами | Редактор вопросов и вариантов с отметками правильных ответов; минимум один правильный; несколько правильных вариантов; Markdown и локальный KaTeX |
| Настройки теста | Лимит попыток, порог правильных ответов, перемешивание вариантов, возврат к вопросам, общий таймер или независимые таймеры вопросов |
| Таймеры вопросов | Только при запрете возврата. Можно указать общее время вопроса по умолчанию и своё время для каждого вопроса |
| Таймер и восстановление | Срок и текущий вопрос хранятся на сервере. Таймер можно скрыть и вернуть. Перезагрузка и закрытие вкладки его не сбрасывают |
| Автосохранение | Код, все редактируемые файлы и ответы сохраняются с версией записи. Есть состояние сохранения, защита от устаревшей вкладки и локальная копия несохранённых изменений |
| Истечение времени | Worker и сервер при обращении фиксируют последнюю сохранённую версию; код отправляется на проверку, ответы оцениваются автоматически, редактирование закрывается |
| STDOUT и unit-тесты | STDOUT: редактируемый `main.cpp`. Unit: `main.cpp`, `task_name.cpp`, `task_name.h`. Для проверки используется закрытый преподавательский main, собственный main — для самостоятельных запусков |
| Эталон | Ввод текста или загрузка `.cpp` UTF-8 до 64 КиБ; проверка эталона на текущем наборе тестов и настроек |
| Форматирование и анализ | clang-format с выбором стиля, cppcheck, AddressSanitizer и UndefinedBehaviorSanitizer. Для каждого инструмента: выключено, замечание либо ошибка, блокирующая зачёт; дополнительно — исключения по кодам диагностик cppcheck и категориям sanitizer/format |
| Запуск и отправка | Запуск с пользовательским stdin не влияет на зачёт. Отправка создаёт отдельную неизменяемую попытку с файлами и результатом |
| Терминальный сценарий | Поддерживаются `make`, `g++ main.cpp -o main`, `./main`, `make test`. Сборка не запускает программу; `make test` проверяет открытые примеры. Закрытые unit-тесты запускаются при отправке |
| Логи | Результат под редактором, stdout/stderr самостоятельных запусков, сообщения компилятора и анализаторов, скачивание лога. Доступ к отчёту закрытых тестов задаётся преподавателем |
| Закрытые данные | Скрытые входы, ожидаемые/фактические ответы и приватная диагностика сборки unit-тестов студенту не передаются. Скачивание использует те же правила, что просмотр |
| Журнал активности | Серверное время переключений вкладок/окон, вставок и терминальных команд; просмотр преподавателем, в том числе в отдельной вкладке |
| Прогресс и проверка | Ведомость своего предмета, история попыток, выбранные ответы, исходники, сборки, отчёты тестов и анализаторов, длительность каждого задания |
| Итог | Для каждого задания учитывается последняя завершённая учебная попытка, успешными должны быть все задания. Без ручного подтверждения — автоматический зачёт; с ним — «ожидает проверки», затем «зачтено» или «на доработке» |
| Комментарий | Общий комментарий преподавателя виден студенту на странице результатов |
| Дополнительная попытка | Выдаётся на одно выбранное задание с записью причины и преподавателя; общего сброса практической работы нет |

Для новых работ используется новый режим отдельных попыток заданий. Старые опубликованные версии и начатые попытки сохраняют прежнюю структуру: они не преобразуются автоматически, их результаты и исходники не теряются. Для проведения зачёта по новым правилам создайте новую работу; старые вопросы свободной теории заменяются заданиями типа «Тест» в библиотеке. При публикации нового режима прежняя теория отклоняется с объяснением.

## Прогнанный сценарий преподавателя и студента

В `tests/practical.browser.mjs` используется настоящий сайт с временной БД и отдельный Docker-worker, без подмены API или результатов проверки.

1. Преподаватель входит, создаёт дисциплину, назначает группу, описание, FAQ и критерии приёма.
2. Создаёт тест и C++-задачу с открытыми и закрытыми тестами, учебным таймером, числом попыток и тремя видами анализа.
3. Создаёт зачёт с датами, группой, баллами, проходным баллом, порогами оценок, линейной цепочкой и подтверждением преподавателя; публикует его.
4. Добавляет опоздавшего студента в уже опубликованный зачёт без перепубликации. Проверяется, что зачёт появляется у него в кабинете.
5. Студент открывает дисциплину, читает правила, проходит тест. Проверяются формулы, сохранение ответов после перезагрузки и скрытие/показ таймера.
6. Студент открывает задачу, пишет код в Monaco, перезагружает страницу и получает сохранённый код.
7. Выполняет `make`, запускает программу на своём вводе, выполняет `make test`, отправляет решение на закрытые тесты и анализаторы. Итог появляется под редактором без ручной перезагрузки.
8. Преподаватель открывает попытку своего студента, видит код, результаты, команды и журнал активности; ставит «на доработке» с комментарием. Студент видит оба значения.
9. Преподаватель ставит «зачтено». Студент видит зачёт, комментарий и оценку 5.

Снимки успешного прогона сохраняются в `test-results/practical-*.png` (каталог исключён из Git).

## Проверки

- 157 серверных тестов Django на отдельной файловой SQLite. В том числе конкурентные старты и отправки одного задания, конкуренция автоотправки с просроченным сохранением, последние завершённые попытки, дедлайны, таймеры вопросов, права и отсутствие утечек закрытых данных.
- 25 автономных проверок runner, резервирования и восстановления.
- 23 интеграционных теста настоящего Docker: корректные и неверные программы, сборка, unit-тесты, отсутствие закрытого main во время запуска, политики форматирования/анализа, UB, лимиты и изоляция.
- 19 прежних браузерных сценариев, включая преподавательские формы; студенческий редактор в этом наборе использует API-фикстуры.
- Дополнительный полный сценарий зачёта с настоящими Django, Chromium и Docker, описанный выше.
- Django system checks, отсутствие незаписанных миграций, синтаксис JavaScript и `git diff --check`.

Команды воспроизведения:

```bash
DEBUG=1 TEST_DATABASE_PATH=/tmp/contest-tests.sqlite3 .venv/bin/python manage.py test lab.tests --noinput
.venv/bin/python -m unittest tests.test_judge_unit tests.test_restore tests.test_backup_offsite
RUN_DOCKER_TESTS=1 JUDGE_IMAGE=contest-judge:requirements .venv/bin/python -m unittest tests.test_docker_integration
BROWSER_PATH=/путь/к/chromium npm run test:browser
BROWSER_PATH=/путь/к/chromium JUDGE_IMAGE=contest-judge:requirements npm run test:practical
```

Для последней команды нужен доступ к Docker. Образ `contest-judge:requirements` для проверки собирается командой `docker build -t contest-judge:requirements judge`; в обычной установке используется настроенный `JUDGE_IMAGE` (по умолчанию `contest-judge:local`).

## Обновление установки

Нужны миграции `0006`–`0009`, новая статика и пересборка образа проверки: в нём добавлены clang-format и cppcheck. До обновления сохраните резервную копию. Для Compose используйте обычное обновление с пересборкой web, worker и judge-image; миграции выполняет init. Для запуска без Compose:

```bash
npm ci
npm run build:editor
DEBUG=1 .venv/bin/python manage.py migrate
DEBUG=1 .venv/bin/python manage.py collectstatic --noinput
docker build -t contest-judge:local judge
```

Перезапустите веб-приложение и worker. Команды миграции/развёртывания на рабочей базе в рамках этой проверки не выполнялись.

## Ограничения и оставшиеся доработки

Основной сценарий зачёта проверен. Полное выполнение каждого пункта исходного списка не заявляется: ограничения реализации, невыполненные работы и состояние обновления перечислены ниже.

Ограничения основных требований:

- Терминал поддерживает только `make`, `make test`, `./main` и `g++ main.cpp -o main`; произвольная shell-сессия не реализована.
- Сохраняются технические пределы: 100 проверочных тестов на C++-задачу, 64 КиБ исходника на файл и 10 000 строк заданий в одном запросе формы. Буквально неограниченные размеры не поддерживаются.
- Старые опубликованные работы и начатые попытки автоматически не переводятся на новый режим. Для новых правил создаётся новая работа.
- Рабочая установка не обновлялась. Миграции `0006`–`0009`, сборка статики, пересборка образа judge и перезапуск процессов остаются шагами развёртывания; команды приведены выше.

Раздел «Последующие доработки» исходного запроса остаётся отдельным бэклогом. В частности, не добавлены новый регламент пересдач после ручного комментария, индивидуальные сроки для групп, автоматическое продление после дедлайна, копирование семестров, массовый архив решений и проверка сходства. Уже существующие версии публикаций, очередь, изоляция, CSV-экспорт, журнал оценок, резервирование и восстановление сохранены.

Другие невыполненные пункты этого бэклога:

- Отдельные права преподавателя на просмотр, проверку, редактирование и управление доступом. Сейчас права задаются доступом к предмету.
- Самостоятельное восстановление пароля через сайт. Пользователи создаются через административные инструменты и импорт; изменение пароля администратором не заменяет такой сценарий восстановления.
- Полный аудит изменений настроек и итогового зачёта. Существующий журнал оценок свободной теории не покрывает все эти действия.
- Отдельные стадии очереди «компилируется» и «проверяется», пользовательское управление остановкой запуска. Существующие статусы очереди и технические ограничения выполнения сохранены.

Для текущей реализации существенны следующие границы:

- Уже начатые задания цепочки остаются доступны. Правила повторной блокировки после неудачной пересдачи, отмены ранее выставленного зачёта и переноса результатов после перестановки заданий требуют отдельного согласования. Порядок начатой работы закреплён её опубликованной версией.
- Комментарий «на доработке» сам по себе не создаёт новые попытки и не продлевает дедлайн. Преподаватель отдельно выдаёт дополнительную попытку выбранного задания; после дедлайна новый старт не разрешается.
- При отсутствии учебного таймера начатая попытка не имеет отдельного срока завершения. Иной срок относится к несогласованным правилам.
- Терминал предоставляет перечисленные учебные команды, каждый запуск пересобирает сохранённые файлы в изоляции. Это не постоянная произвольная shell-сессия.
- `make test` использует открытые примеры. Если их нет, сайт объясняет это; закрытые тесты запускаются только при отправке.
- Для скрытых проверок студент получает безопасный отчёт с количеством и вердиктами тестов при включённом доступе; сырые скрытые stdout/stderr и данные тестов не раскрываются. Динамический анализ закрытых тестов показывает безопасное резюме.
- Учебного ограничения в 100 заданий на практическую работу нет; защита обработки форм ограничивает один запрос 10 000 строками. Вопросы нового теста хранятся списком без отдельного учебного лимита. Существующий технический предел тестовых случаев C++-задачи — 100, исходника каждого файла — 64 КиБ.
- Нагрузочная репетиция 30 студентов из прежней документации не повторялась для нового режима и анализаторов; новые браузерные сценарии проверяют функциональность, а не производственную ёмкость.
