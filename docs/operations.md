# Эксплуатация

## Резервная копия

Используется SQLite backup API: копирование согласовано с активными транзакциями и WAL. Простое копирование живого `db.sqlite3` может потерять данные из WAL.

```bash
docker compose exec web python manage.py backup_database /data/backup-2026-10-26.sqlite3
docker compose cp web:/data/backup-2026-10-26.sqlite3 ./backup-2026-10-26.sqlite3
chmod 600 ./backup-2026-10-26.sqlite3
```

Имя файла должно быть новым. Команда проверяет целостность и ставит права 0600. Копию со служебного volume после выгрузки можно удалить. Сохраняйте копии за пределами сервера и проверяйте восстановление. Отдельно сохраняйте `.env`, исходники/образы развёрнутой версии и TLS volume Caddy при необходимости.

## Восстановление

Вначале остановите приём запросов и worker. Сохраните текущую базу перед заменой. Ниже предполагается, что файл копии находится в текущей папке хоста. Скрипт читает его через stdin в остановленный Compose volume и отказывается перезаписывать уже сохранённую аварийную копию.

```bash
docker compose stop proxy web worker
# При изменении пути замените только имя файла слева от перенаправления.
docker compose run --rm -T --no-deps web python scripts/restore_database.py < backup-2026-10-26.sqlite3
docker compose run --rm init
docker compose up -d web worker proxy
```

Для новой установки сначала соберите образы и задайте тот же secret. После восстановления проверьте вход, число попыток и опубликованные версии. Worker переведёт восстановленные выполнявшиеся задания в ошибку инфраструктуры; повторите их в админке. Очередь из резервной копии сохранится.

## Мониторинг

Войдите преподавателем и откройте `/teacher/judge/`. Панель показывает очередь, последнюю активность worker и инфраструктурные ошибки с кнопкой повторной проверки. Запись состояния создаётся после захвата эксклюзивной блокировки worker. Сигнал обновляется каждые 5 секунд отдельным соединением с SQLite и во время компиляции/тестов; после 30 секунд без сигнала для активного процесса выводится «Нет свежего сигнала». Это не повод автоматически повторять выполняющуюся отправку: проверьте процесс и журнал. Статусы штатной остановки и ошибки сохраняются явно. Недоступность обновления самой панели помечается как устаревшие данные.

```bash
docker compose ps
docker compose logs --tail=100 worker web proxy
docker compose exec web python manage.py check --deploy
docker compose exec web python manage.py shell -c 'from lab.models import Submission; from django.db.models import Count; print(list(Submission.objects.values("status").annotate(count=Count("id"))))'
docker system df
```

Проверьте свободное место, число `queued`/`running`, перезапуски worker и наличие `infra_error`. Ошибки Docker не означают ошибку студента. Действие «Повторить проверку» сохраняет исходник и время исходного приёма. Не очищайте все Docker volumes командой глобального prune на учебном сервере: там могут находиться база и сертификаты.

Остановка worker через SIGTERM очищает текущие ресурсы. После SIGKILL очистку выполняет следующий запуск по метке `department.contest.judge=<JUDGE_PREFIX>`. Один процесс на установку удерживает файловую блокировку `/data/worker.lock`.


Каталог `backups` создайте заранее, имя копии должно быть новым. После запуска проверьте `/teacher/`, ведомость старой версии и `/teacher/judge/`. Для отката восстановите копию базы вместе с предыдущей версией кода; не удаляйте вручную поля из рабочей базы.

## Перед первым зачётом

Выполните все команды тестирования из README, затем пройдите демонстрационный зачёт студентом. Отправьте корректный код, дождитесь Docker-вердикта, завершите работу, оцените теорию и проверьте итог. Проверьте резервное копирование и восстановление на отдельной копии установки. Повторите тест 30 студентов на конфигурации рабочего сервера; размер очереди и время её обработки зависят от реальных тестов и лимитов задач.

## Защита сохранений и обновление схемы

Миграция `lab.0003` добавляет версии черновиков/ответов и уникальный идентификатор запроса отправки. Перед обновлением сделайте согласованную копию, остановите веб и worker, примените миграции и обновите статику по процедуре из README. После обновления студенты должны перезагрузить открытые страницы: старый JavaScript не передаёт обязательные версии текста.

Две вкладки не могут молча перезаписать разные тексты. При конфликте автосохранение поля приостанавливается; студент сравнивает локальный и серверный текст, включая связь теории с отправкой, и выбирает нужный. Повтор идентичного сохранения безопасен. Изменение преподавателем оценки не меняет версию самого ответа.

Запросы браузера ограничены 15 секундами, включая получение тела ответа. Таймаут не означает отмену операции на сервере. Неподтверждённая отправка сохраняет исходник, вид запуска, ввод и идентификатор операции в браузере. Кнопка «Повторить запрос» возвращает ту же отправку без расхода новой попытки, в том числе после дедлайна, если исходный запрос был принят вовремя. До разрешения неопределённости новые запуски и завершение работы приостановлены; редактирование доступно. При недоступном локальном хранилище повтор возможен в текущей странице; перед перезагрузкой проверьте историю отправок. Повтор завершения уже закрытой попытки возвращает её итог без изменения сохранённых полей.

## Репетиция с настоящим Docker и браузером

Запускайте из каталога проекта в установленном виртуальном окружении на Linux с доступным Docker и собранным `contest-judge:local`. Скрипт использует отдельную временную базу, отдельный префикс контейнеров и локальный порт. Рабочая база и студенты не используются. Перед созданием данных проверяется Docker и наличие образа.

```bash
# Полная браузерная сдача: настоящий Django, Monaco, Docker, теория и итог.
BROWSER_PATH=/usr/bin/chromium .venv/bin/python scripts/rehearse_exam.py --students 1 --browser --report test-results/exam-browser.json

# 30 одновременных студентов через HTTP и Gunicorn (2 процесса, 4 потока).
.venv/bin/python scripts/rehearse_exam.py --students 30 --restart-worker --report test-results/exam-load.json
```

Каждый студент входит, начинает попытку, сохраняет код, дважды повторяет один запрос отправки, связывает теорию с кодом и дважды завершает работу. После реальной проверки преподаватель выставляет оценку через HTTP, проверяется окончательный зачёт. Режим `--restart-worker` останавливает занятый worker, проверяет `infra_error`, запускает worker заново и возвращает ту же отправку в очередь через кабинет. Если очередь успела закончиться до прерывания, сценарий завершится ошибкой, не выдавая это за проверенное восстановление.

В конце создаётся согласованная копия временной базы и восстанавливается в другую базу; сравниваются количество попыток и выставленных оценок. Процессы и ресурсы Docker убираются при выходе. Отчёт содержит p95 HTTP-запросов, максимальное ожидание очереди и длительность проверки. Ограничение ожидания очереди — 600 секунд, меняется через `--timeout`. Любая неожиданная HTTP-ошибка, лишняя отправка или непринятый код завершает сценарий с ненулевым кодом.

Это нагрузка на одной небольшой задаче сложения с тремя тестами. Пропускную способность на задачах кафедры нужно измерить отдельно; время компиляции и число тестов влияют на очередь. Существующие 13 Docker-тестов дополнительно проверяют лимиты и изоляцию, а 13 браузерных сценариев с подменой API — ошибки сети, конфликты вкладок и восстановление неподтверждённой отправки.

## Ежедневная копия с выгрузкой за пределы сервера

`scripts/backup_offsite.py` вызывает SQLite backup API через работающий Compose, выгружает копию на хост и отправляет её через `scp` в заранее созданный приватный каталог на другом сервере. SSH использует ключ и `BatchMode`: запрос пароля считается ошибкой. Успех записывается только после успешной выгрузки. При успешной выгрузке остаются 14 последних локальных копий; при ошибке выгрузки старые копии не удаляются. Хранение удалённых копий настраивается на сервере резервирования.

В `deploy/contest-backup.service` указан каталог проекта `/srv/contest`; замените его на фактический в обоих аргументах `ExecStart`. Служба запускается от root и использует его настроенный SSH-ключ и `known_hosts`. Создайте `/etc/contest-backup.env` с правами 0600:

```ini
CONTEST_BACKUP_DIR=/var/backups/contest
CONTEST_BACKUP_REMOTE=backup-user@backup-host:/srv/backups/contest
```

После настройки адреса и SSH сначала выполните разовую проверку, затем включите таймер:

```bash
sudo install -m 644 deploy/contest-backup.service deploy/contest-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start contest-backup.service
sudo systemctl status contest-backup.service
sudo systemctl enable --now contest-backup.timer
sudo systemctl list-timers contest-backup.timer
sudo journalctl -u contest-backup.service --since today
```

Таймер запускается ежедневно около 03:00 по времени сервера и восполняет пропущенный запуск после включения. Для внешнего мониторинга используйте команду ниже: ненулевой код означает отсутствие подтверждённой копии за последние 26 часов или отсутствие локального файла. Проверяйте также состояние `contest-backup.service`; сбой свежей выгрузки отражается сразу, даже пока предыдущая копия укладывается в 26 часов.

```bash
sudo python3 /srv/contest/scripts/backup_offsite.py --directory /var/backups/contest --check
```

Установка таймера и реальная SSH-выгрузка в рабочем окружении автоматически не выполняются: адрес сервера резервирования и доступы задаёт администратор. Проверяйте восстановление копий на отдельной установке по процедуре выше.


## Контроль worker, очереди и резервной копии

Для внешнего планировщика выполните команду внутри установленной среды приложения:

```bash
docker compose exec -T web python manage.py check_exam
```

Команда печатает JSON: `healthy`, `queued`, `running`, `oldest_seconds`, `heartbeat_at`, `warnings`. Код 0 означает свежий сигнал работающего worker и ожидание менее `QUEUE_WARNING_SECONDS` (по умолчанию 120 секунд). Код 1 означает проблему; остановленный worker тоже считается проблемой. Внешний планировщик должен вызывать команду, например, раз в минуту и уведомлять администратора при ненулевом коде. Сведения о студентах и их программах в JSON не включаются.

Копии из systemd-примера находятся на хосте, поэтому их проверяют на хосте:

```bash
sudo python3 /srv/contest/scripts/backup_offsite.py --directory /var/backups/contest --check
```

Если каталог подтверждённых копий доступен процессу Django, можно объединить проверки: `python manage.py check_exam --backup-directory /путь/к/копиям`. Не передавайте путь хоста в контейнер без соответствующего монтирования. Проверка копии контролирует маркер успешной SSH-выгрузки и возраст до 26 часов; она не заменяет пробное восстановление и контроль состояния systemd-службы.

## Репетиция собственного задания

Сохраните приватный JSON UTF-8 с полями `title`, `statement`, `reference_source`, `tests`. Каждый тест содержит `input`, `expected`, необязательно `label` и `is_sample`. Дополнительные поля задачи — `time_limit` (секунды) и `memory_mb`. Должен быть хотя бы один скрытый тест. Файл содержит закрытые тесты и эталон; задайте ему права 0600.

```bash
.venv/bin/python scripts/rehearse_exam.py --students 30 --restart-worker \
  --problem-json /закрытый/путь/problem.json --report test-results/department-load.json
```

Сначала настоящий worker проверяет эталон, затем все виртуальные студенты отправляют его через HTTP. Рабочая база не используется. Отчёт содержит число тестов и лимиты, длительность проверки, ожидание очереди и p95 HTTP. При длинных тестах увеличьте `--timeout`; он ограничивает ожидание опустошения очереди. Режим собственного задания проверяет HTTP/Docker; `--browser` использует встроенную демонстрационную задачу.

Проверенные 57.9 с ожидания для 30 студентов относятся к демонстрационной задаче с тремя тестами. Сравнивайте результаты на одинаковом оборудовании и сопоставимых заданиях; эти цифры не являются гарантией для работы с сотней тестов.

## Обновление с журналом оценок

Миграция `lab.0004` добавляет журнал, очередь эталонов и счётчики входа. Используйте процедуру обновления в README с остановкой web/worker и предварительной резервной копией. ## Курсы и независимые преподаватели

Миграция `lab.0005_courses` добавляет курсы и обязательную принадлежность задач и работ. Перед обновлением остановите web и worker, создайте согласованную резервную копию, обновите код, выполните `migrate` и `collectstatic`, затем запустите процессы по процедуре README. После обновления перезагрузите открытые страницы преподавателей.

На существующей установке все прежние задачи, работы и группы переносятся в «Общий курс (перенесённые данные)». Доступ к нему получают существующие активные преподаватели. Опубликованные снимки, сроки, попытки, отправки и оценки не переписываются. Это сохраняет прежний общий доступ к старым материалам; новые преподаватели автоматически к общему курсу не добавляются. Суперпользователь должен проверить его список преподавателей и при необходимости убрать лишних. Новые независимые работы создавайте в отдельных курсах.

Преподаватель создаёт курс через кабинет или административную форму и автоматически становится его преподавателем. Только суперпользователь меняет список преподавателей. Для совместного ведения назначьте нескольких преподавателей одному курсу. Отзыв членства сразу закрывает доступ к его данным, включая ранее открытые ссылки. Суперпользователь видит все курсы.

Суперпользователь может назначать курсу существующие учебные группы. Преподаватель добавляет новых студентов через импорт CSV с выбором курса; новые группы автоматически включаются в него. При совпадении названия с недоступной группой импорт отклоняется целиком: используйте уникальное название или попросите суперпользователя назначить существующую группу. Общие логины, пароли и членства студентов изменяет суперпользователь, поскольку одна учётная запись может использоваться в нескольких курсах.

После обновления проверьте под двумя преподавателями разные курсы: списки в кабинете и админке, ведомости и CSV, исходники и результаты, оценивание, продление, эталоны и повтор проверки. Оба преподавателя должны видеть только свои учебные данные. Состояние worker остаётся общим, а список отправок и счётчики очереди в кабинете ограничены доступными курсами. Системная команда `check_exam` контролирует всю установку.
